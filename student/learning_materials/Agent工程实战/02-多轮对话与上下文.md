# 项目 2：让 AI 记住刚才说了什么——多轮对话与上下文管理

## 一、我们要解决什么问题

上一节我们成功让 AI 回答了一个问题。但你有没有发现：**每次运行 `python app.py`，AI 都不记得你上一轮问了什么**。

试试看：先问「我叫小林」，再问「我叫什么名字？」——AI 会说「我不知道你的名字」。这不像在聊天，更像是每次都在和陌生人说话。

### 为什么模型会「失忆」？

> 🧠 **关键概念：LLM 是无状态的。** 每一次 `model.invoke(messages)` 都是一个**独立的 HTTP 请求**。服务器处理完你的请求后就「忘记」了——就像你每次打电话给客服，对方都不知道你上一通电话说了什么。

模型本身没有「记忆芯片」。它不会在服务器端帮你保存对话历史。**让模型「记住」上下文的唯一方法，就是把历史对话重新塞进下一次请求的 `messages` 列表里。**

```text
第1轮：发送 [system, user:"我叫小林"]                    → 模型回答 "好的，小林"
第2轮：发送 [system, user:"我叫小林", assistant:"好的，小林", user:"我叫什么?"]  → 模型回答 "你叫小林"
```

看到了吗？第二轮把第一轮的**完整对话**（用户说了什么 + 模型答了什么）一并发送，模型才能「想起来」。

### 本节目标

1. **先理解**：为什么 HTTP 请求需要手动传历史
2. **再实现**：在 `app.py` 中写出带 `while True` 循环的聊天程序
3. **后整理**：把历史追加 + 裁剪提取为 `append_turn_and_trim` 函数
4. **最终验收**：验证多轮记忆、上下文裁剪和输入不可变

## 三、先写出能多轮对话的程序

### 3.1 理解消息列表的「角色循环」

在动手写代码之前，先理解消息列表应该长什么样。LangChain 使用 OpenAI 定义的三段式角色协议：

```text
[
  {"role": "system", "content": "你是课程助教..."},       ← 只出现一次，定义规则
  {"role": "user", "content": "我叫小林"},                ← 第1轮用户
  {"role": "assistant", "content": "好的，小林！"},       ← 第1轮 AI
  {"role": "user", "content": "我叫什么名字？"},           ← 第2轮用户
  {"role": "assistant", "content": "你叫小林。"},          ← 第2轮 AI
]
```

> 🧠 **角色循环规律**：`system` 放最前面（只出现一次），之后是 `user → assistant → user → assistant → ...` 交替出现。如果某轮只追加了 `user` 而没追加 `assistant`，下一轮模型就看不到自己刚才说了什么——它会对自己的回答「失忆」。

### 3.2 写出聊天循环（`app.py`）

复用上一节的模型初始化代码，然后加入 `while True` 循环：

```python
# app.py —— 多轮对话版
import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI

load_dotenv()

api_key = os.getenv("LLM_API_KEY")
if not api_key:
    raise RuntimeError("缺少 LLM_API_KEY，请先在 .env 中填写你的 API Key")

model = ChatOpenAI(
    model=os.getenv("LLM_MODEL", "deepseek-chat"),
    api_key=api_key,
    base_url=os.getenv("LLM_BASE_URL", "https://api.deepseek.com"),
    temperature=0.2,
    timeout=30,
    max_retries=2,
)

# 关键变化：messages 不再是写死的一次性列表，而是贯穿整个对话的「状态容器」
messages = [
    {"role": "system", "content": "你是课程助教。信息不足时先追问，不要编造。"}
]

print("开始聊天（输入 exit 或 quit 退出）\n")

while True:
    # 1. 读取用户输入
    user_text = input("你：").strip()
    if user_text.lower() in {"exit", "quit"}:
        print("再见！")
        break
    if not user_text:
        print("请输入内容")
        continue

    # 2. 把用户消息追加到历史
    messages.append({"role": "user", "content": user_text})

    # 3. 把完整历史发给模型（这是「记忆」的关键！）
    response = model.invoke(messages)
    answer = str(response.content)

    # 4. 把模型回答也追加到历史（下一轮它才能看到自己答了什么）
    messages.append({"role": "assistant", "content": answer})

    print(f"AI：{answer}\n")
```

> 🧠 **为什么 user 和 assistant 都要追加？** 如果只追加 user、不追加 assistant，下一轮模型就看不到自己刚才的回复。它可能会重复回答、前后矛盾，或者在追问时「忘记」自己已经确认过的事情。

运行它：

```bash
python app.py
```

测试记忆：先输入「我叫小林」，再输入「我叫什么名字？」。如果 AI 回答「你叫小林」，说明多轮记忆生效了！

### 3.3 理解这段代码做了什么

| 代码 | 作用 | 为什么这样设计 |
|------|------|---------------|
| `messages = [{...}]` | 在循环外初始化消息列表 | 它贯穿整个对话生命周期——就像一个「聊天记录本」，每轮往里追加 |
| `messages.append({"role": "user", ...})` | 把用户输入写入记录本 | 下一轮调用 `model.invoke(messages)` 时，模型会看到它 |
| `messages.append({"role": "assistant", ...})` | 把模型回答也写入记录本 | 如果不写，下一轮模型不知道它自己刚才说过什么 |
| `model.invoke(messages)` | 每次发送**完整**历史 | 这是 HTTP 无状态协议下的唯一「记忆」手段 |

## 四、问题来了：消息列表会无限增长

### 4.1 上下文窗口——AI 的「注意力上限」

> 🧠 **关键概念：上下文窗口（Context Window）** 是模型一次能「看到」的最大文本量。DeepSeek 的上下文窗口是 128K tokens（约 10 万字），看起来很大——但如果用户聊了 200 轮，消息历史还是会超出窗口。超出的部分会被**截断**，模型就会「忘记」最早的内容。

而且，把几万字的聊天历史每次都发给模型，**每次请求的费用和延迟都会越来越高**。

### 4.2 裁剪策略：保留 system + 最近 N 条

解决方案：**在每次调用模型之前，裁剪消息列表**——保留开头的 `system` 消息（角色定义不能丢），只保留最近的若干条对话消息。

```python
def trim_messages(messages, max_messages=11):
    """裁剪消息列表：保留 system + 最近 N 条。
    
    参数 max_messages=11 的含义：
    - 奇数上限确保 system + (user, assistant) 成对出现
    - 例如：1条system + 5对(user,assistant) = 11条
    """
    if len(messages) <= max_messages:
        return list(messages)  # ← 返回新列表，不修改原列表
    
    # 保留 system 消息（如果存在）
    system = messages[:1] if messages and messages[0].get("role") == "system" else []
    # 剩余配额给最近的普通消息
    remaining = max_messages - len(system)
    return system + messages[-remaining:]
```

在每次调用模型前执行：

```python
messages = trim_messages(messages)
```

> 🧠 **为什么要返回新列表而不是直接删？** 这是「不可变数据」原则——调用方传入的原始列表不应被函数偷偷修改。如果 `trim_messages` 直接 `del messages[1]`，调用方的变量也会变，调试时会非常困惑。工程代码优先返回新值，让状态变化发生在**明确的一行赋值语句**。

## 五、提取 `append_turn_and_trim`——从「能用」走向「可测试」

现在把「追加本轮对话 + 裁剪」的逻辑提取为独立函数。

### 5.1 为什么要提取？

在 `app.py` 中，追加和裁剪是混在聊天循环里的。如果我们想单独验证「裁剪逻辑是否正确处理了有/无 system 的历史」，每次都得启动整个聊天程序——又慢又难覆盖边界情况。

> 🧠 **工程思维**：把纯数据变换的逻辑（追加消息 + 裁剪长度）提取为独立函数后，测试不需要网络、不需要模型、不需要 API Key，毫秒级覆盖所有边界用例。这就是上一节「I/O 与纯逻辑分离」的延续。

### 5.2 实现 `append_turn_and_trim`

在 `solution.py` 中写入：

```python
# solution.py —— 多轮对话上下文管理
def append_turn_and_trim(history, user_text, assistant_text, max_messages):
    """追加一轮对话并裁剪到指定长度，返回新列表。
    
    参数：
        history (list[dict]): 当前消息历史，每项含 role 和 content
        user_text (str): 本轮用户输入
        assistant_text (str): 本轮模型回答
        max_messages (int): 裁剪后最多保留的消息条数（必须 >= 2）
    
    返回：
        list[dict]: 裁剪后的新消息列表（不修改原 history）
    
    异常：
        ValueError: 参数非法时抛出（类型错误、空字符串、max_messages < 2 等）
    
    核心规则：
        1. 绝不能修改传入的 history —— 始终返回新列表
        2. 如果 history 第一条的 role 是 "system"，裁剪时必须保留它
        3. system 消息不参与「从尾部取最近消息」的计数
        4. max_messages 是「包括 system 在内」的总条数上限
    """
    # 1. 输入校验 —— 门禁原则：先检查再处理
    if not isinstance(history, list):
        raise ValueError("history 必须是列表")
    if not isinstance(user_text, str) or not user_text.strip():
        raise ValueError("user_text 必须是非空字符串")
    if not isinstance(assistant_text, str) or not assistant_text.strip():
        raise ValueError("assistant_text 必须是非空字符串")
    if not isinstance(max_messages, int) or max_messages < 2:
        raise ValueError("max_messages 必须是 >= 2 的整数")
    
    # 校验 history 中每条消息的结构
    for i, msg in enumerate(history):
        if not isinstance(msg, dict) or "role" not in msg or "content" not in msg:
            raise ValueError(f"history[{i}] 缺少 role 或 content 字段")
    
    # 2. 创建新列表（不可变原则：绝不修改传入的 history）
    new_history = list(history)
    
    # 3. 追加本轮对话
    new_history.append({"role": "user", "content": user_text.strip()})
    new_history.append({"role": "assistant", "content": assistant_text.strip()})
    
    # 4. 裁剪到 max_messages
    if len(new_history) <= max_messages:
        return new_history
    
    # 检查第一条是否为 system
    has_system = new_history[0].get("role") == "system" if new_history else False
    
    if has_system:
        # 保留 system，从尾部取剩余配额
        system_msg = new_history[0]
        remaining = max_messages - 1  # 给 system 留一个位置
        return [system_msg] + new_history[-(remaining):]
    else:
        # 没有 system，直接从尾部取
        return new_history[-max_messages:]
```

**设计要点**：

- ✅ **不可变**：用 `list(history)` 创建浅拷贝，原列表不受影响
- ✅ **门禁校验**：先检查所有参数合法性，再处理数据——防止「垃圾进、垃圾出」
- ✅ **system 保护**：裁剪时永远保留 system 消息，否则模型角色会漂移
- ✅ **奇数上限**：`max_messages=11` 意味着 1 条 system + 5 对 (user, assistant)，保证消息成对

在编程实验室中点击阶段检查，系统会运行测试覆盖有/无 system、边界裁剪、非法输入等场景。

## 六、重构 `app.py`——接入提取好的函数

现在把 `app.py` 中的追加和裁剪逻辑替换为函数调用：

```python
# app.py —— 重构版
import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from solution import append_turn_and_trim   # ← 新增

load_dotenv()

api_key = os.getenv("LLM_API_KEY")
if not api_key:
    raise RuntimeError("缺少 LLM_API_KEY，请先在 .env 中填写你的 API Key")

model = ChatOpenAI(
    model=os.getenv("LLM_MODEL", "deepseek-chat"),
    api_key=api_key,
    base_url=os.getenv("LLM_BASE_URL", "https://api.deepseek.com"),
    temperature=0.2,
    timeout=30,
    max_retries=2,
)

messages = [
    {"role": "system", "content": "你是课程助教。信息不足时先追问，不要编造。"}
]

print("开始聊天（输入 exit 或 quit 退出）\n")

while True:
    user_text = input("你：").strip()
    if user_text.lower() in {"exit", "quit"}:
        print("再见！")
        break
    if not user_text:
        print("请输入内容")
        continue

    # 调用模型（先用当前历史获取回答）
    response = model.invoke(messages)
    answer = str(response.content)

    # ← 重构点：用函数调用替代原来的手动 append + 手动裁剪
    messages = append_turn_and_trim(
        history=messages,
        user_text=user_text,
        assistant_text=answer,
        max_messages=11,
    )

    print(f"AI：{answer}\n")
```

> ⚠️ **注意顺序**：这里是先 `invoke(messages)` 获取回答，再调用 `append_turn_and_trim`。因为 `append_turn_and_trim` 会同时追加 user 和 assistant——如果先追加再调用模型，模型会看到一条空的 assistant 消息。

在终端再次运行 `python app.py`，先输入「我叫小林」，再问「我叫什么？」，确认模型能引用前文。

## 七、常见错误速查

| 现象 | 可能原因 | 排查方法 |
|------|---------|---------|
| 第二轮模型不记得第一轮内容 | 只追加了 user、没追加 assistant | 检查 `messages.append` 是否成对出现 |
| 裁剪后模型角色漂移（突然说「作为AI我不能…」） | system 消息被裁剪掉了 | 确认裁剪逻辑中有「保留 system」的分支 |
| 聊天越来越慢、越来越贵 | 历史消息没有裁剪，每次发送几万字 | 确认每次 `invoke` 前调用了裁剪函数 |
| 裁剪后对话不完整 | max_messages 设得太小，或为偶数导致消息不成对 | 使用奇数上限（如 11 = 1+5×2） |
| 测试时发现原列表被修改 | 函数内部直接操作了传入的 history | 确认使用 `list(history)` 创建副本 |
